## Selected reconstruction: active persistence only

- `companycodes.organizationid` is the organization key. `users.organizationid` and `projects.organizationid` reference it. Names remain where the active controller stores them; developer organizationname can be NULL. No organization normalization/refactor is introduced.
- `users.id` is text PK; `projects.id` is UUID PK. The controller generates both values; no UUID extension or invented server ID generator is required.
- Unique index on `lower(users.email)` prevents duplicate identities regardless of email casing. Controller normalizes emails; duplicate inserts currently return its existing 500 response rather than a new conflict response. That application error contract is deferred.
- Nonempty checks on required names/IDs/email/role/status and ordinary NOT NULL constraints prevent unusable core rows. Role/status enums are **not** invented; role authorization is not modernized through database checks.
- A nullable assignment must identify an existing user **in the project's organization** via a composite FK to `(users.id, users.organizationid)`; a supporting unique key and filter/FK indexes are new integrity decisions. No cascading deletes are introduced; referenced organization/user deletions are restricted.
- Project status is NOT NULL because the active list uses GetString without checking NULL. A database default of `active` supports direct SQL inserts that omit it. The recovered API explicitly sends DBNull when Status is omitted, so the default does **not** repair that API case. Smoke requests supply a real status.
- Assignment is SQL NULL for unassigned projects. The frontend can send an empty string; the unchanged controller does not normalize it and the FK will reject it. Smoke tests cover explicit NULL and valid assignments; this UI/API mismatch is recorded for M3, not hidden with a fake empty-ID user.
- No business data is seeded by initialization. Repeatable smoke tests create only synthetic names and reserved `example.test` identities with per-run random passwords. The schema marker table `portfolio_schema_versions` is new setup metadata, not academic business functionality.
- The Docker bootstrap account owns DDL; a separate application role gets only schema usage and CRUD on the four application tables, plus SELECT on schema metadata. It has no superuser, role/database-creation, or public-schema CREATE rights. This is connection privilege setup, **not** application-user authentication/authorization modernization.
