## SDK decision

Microsoft's [stable .NET 10 downloads](https://dotnet.microsoft.com/en-us/download/dotnet/10.0) and [official release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/10.0/releases.json), checked October 28, identify SDK **10.0.403**, release October 25, with .NET/ASP.NET Core/Desktop runtimes **10.0.14**, active LTS. Windows and process architecture were both x64. The owner explicitly approved system-wide side-by-side installation; older SDKs/runtimes remain installed. The downloaded Windows installer matched Microsoft's SHA512 and had a valid Microsoft Corporation Authenticode signature immediately before execution. Installer exit 0; no restart required or initiated. Verification and installer result are ignored `.local/m5a-sdk` evidence.

`global.json` selects 10.0.403, latestPatch roll-forward and no prerelease. This keeps this project on the tested 10.0.4xx feature band while permitting servicing updates, without selecting the unrelated .NET 11 preview channel. Only CLI workflows are in scope; Visual Studio IDE compatibility is not yet verified.

## Scoped compatibility and dependency decisions

- Backend and four active project-reference helpers (LocalAdministrator, SecurityRegressionProbe, BrowserWorkflowFixture, GraphIntegrationProbe) target net10.0. Their launch/identity paths use net10.0. Historical independent HttpIntegrationProbe remains net8.0 and must not be run against the secured current API; the antivirus-blocked PowerShell script is preserved and never executed.
- WindowsServices package 9.0.2 -> 10.0.14 aligns framework-host integration with the supported .NET 10 servicing line. Npgsql 9.0.3 and BCrypt.Net-Next 4.0.3 remain unchanged; their published target frameworks support newer runtimes, with actual compatibility requiring the tests below.
- Microsoft.Data.Sqlite 7.0.0, Dapper 2.0.123 and Newtonsoft.Json 13.0.3 had no source API/import/reflection calls in the backend or helpers. Remove these unused references, then verify compilation and runtime behavior. The dormant SQLite-named backup service uses only BCL file copying, is unregistered, and remains retained without its package; no PostgreSQL backup is added.
- The pre-upgrade official NuGet audit reported high-severity SQLitePCLRaw.lib.e_sqlite3 **2.1.2**, transitive through Microsoft.Data.Sqlite. [GHSA-2m69-gcr7-jv3q](https://github.com/advisories/GHSA-2m69-gcr7-jv3q) covers versions <=2.1.11 and lists no patched NuGet version. Removing an unused dependency is preferable to inventing a patched version or changing database architecture. Audit the complete post-restore graph again; do not infer absence from a successful build.
- [.NET 10 API cookie behavior](https://learn.microsoft.com/en-us/aspnet/core/breaking-changes/10/cookie-authentication-api-endpoints?view=aspnetcore-10.0) returns 401/403 for known API endpoints. Existing DatabaseCookieEvents explicitly implements those statuses, so retain it and verify no redirect regression. Keep server-side tickets, DB membership/password-version revalidation, revocation, secure cookies, CSRF and middleware order unchanged.
- [BackgroundService startup changes](https://learn.microsoft.com/en-us/dotnet/core/compatibility/extensions/10.0/backgroundservice-executeasync-task) move all ExecuteAsync work off the startup thread. The active Worker only logs a heartbeat; database startup validation is explicitly awaited separately in Program.cs, so no initialization dependency needs to be moved.
- Keep AddControllersWithViews/global antiforgery, fixed loopback HTTPS, explicit localhost CORS, parameterized Npgsql SQL/JSONB, BCrypt limits/work factor, explicit graph allowlists/revisions, safe errors and DPAPI-protected private keys. No authentication, authorization or schema redesign is planned. Recheck JSON validation and session behavior with real HTTP/Edge tests.

## Rollback procedure

1. Stop only the independently verified task API/frontend processes. Preserve the current changed files separately and compare hashes with this milestone's final change inventory so unrelated later work is not overwritten.
2. Restore the milestone-modified existing project/scripts/browser-runner files byte-for-byte from `.local/m5a-baseline-20261028/source`, checking their original hashes against `manifest.json`. Restore earlier documentation only if a full documentation rollback is intended; preserve later unrelated edits.
3. For an exact SDK rollback, replace only the milestone-created global.json with an SDK 8.0.206 pin (latestPatch, no prerelease) and verify `dotnet --version` before restoring/building. The original tree had no global.json; removing the new pin alone restores that source layout but lets the highest globally installed SDK select, which is now 10.0.403. Any removal must be limited to the unchanged task-created file; do not delete other files or reset Git/history.
4. Use retained SDK 8.0.206 to restore the original net8.0 backend/helper packages and build Release. Existing dependencies may need restoring because project.assets.json is generated for the selected target. Run the original guarded security/graph/browser procedures and frontend checks before claiming rollback verified.
5. No database migration/restore/reset is part of rollback: schema 1/2/3 and project volume remain the same. Restore no secrets or credentials from the source snapshot. The approved .NET 10 SDK may remain side by side; removing system software requires a separate explicit decision.

The final hash inventory is `.local/m5a-final-change-inventory.json`, including original/current hashes for modified files and hashes of new files. Compare current content against it before any rollback; stop if later work changed a target. Rollback is a documented file-based recovery procedure, not a destructive reset, and was not executed during the successful upgrade. Restoring the original package graph also restores the known unused SQLite advisory; use that state only to diagnose/regain the earlier baseline, not as a claim of vulnerability remediation.
