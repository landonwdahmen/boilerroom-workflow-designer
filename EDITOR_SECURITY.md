## Planned bounded repairs

1. Remove the entire browser executor, arbitrary fetch, dynamic evaluation, execution shortcut/result console/toast and misleading generation help. Retain all six node categories as **configuration-only** with explicit disabled/not-implemented labels; no substitute executor or sandbox package.
2. Use each existing type's registered renderer and correct source/target handle direction. Derive selected properties from current graph state, associate labels, keep deletion edges consistent and enforce bounded known types/properties/connections. Add errors, selection deletion and empty-state guidance.
3. Keep the backend-scoped project lookup authoritative for visibility, invalidate results on project/identity changes and recheck on focus. Administrators edit local drafts; developers have read-only inspection, no add/connect/move/delete/property/keyboard mutation. No endpoint, schema or developer editing permission added.
4. Meaningful state/property/security/permission tests, installed Edge editing interactions and M3A/M3B regressions. Test malicious content only as inert synthetic text, with no external requests or execution. Preserve own fixtures and original M2 row.
5. Document a minimal **proposed** M4B PostgreSQL graph contract, including permissions/limits/concurrency, without implementing it.

## M4A implementation contract

- All six existing categories render through ApiNode with their actual type ID. Triggers have one output, responses one input, other nodes one of each. SQL Table remains metadata; the dormant table renderer is not activated.
- The entire executor is removed: no dynamic-code construction/eval, graph-driven fetch, generation/run shortcut, result console or simulated success toast. Ctrl/Cmd+R is normal browser refresh. Code/query/URL/header/body values are bounded **inert text**, rendered through React escaping, not HTML, templates or executable handlers. Do not enter real secrets.
- An atomic local reducer handles nodes and edges together, pruning incident edges on node deletion. The selected node is derived from current graph state; PropertyEditor has no stale shadow copy. It supports input associations, read-only inspection and validation messages. JSON fields remain editable strings and are parsed only for non-executing shape validation.
- Addition supports the existing type-ID native drop and an accessible palette button. Unknown types/IDs/properties, nonfinite/out-of-bounds coordinates and unlisted methods are rejected. Limits are 100 nodes, 200 edges, 100-character labels, 4096 characters/property and absolute coordinates <=100000. Connections require existing endpoints, correct handles/direction, no self-links, duplicates or cycles. These are local-draft consistency rules, not an execution engine or server trust boundary.
- Node movement, edge selection/removal and node/selection deletion use the installed React Flow callbacks. Delete/Backspace is restricted to editable canvas selection; text-entry keys retain native behavior. The built-in interactivity toggle is hidden so it cannot unlock developer controls.
- Backend cookie-authenticated, DB-scoped project lookup gates visibility. Route/user/role/organization changes invalidate old access synchronously; focus rechecks permissions. Pending focus checks temporarily disable editing while preserving the same valid local draft. Failed/revoked access removes the editor; no client project ID/role supplies backend authority.
- Administrators may edit the verified own-organization local draft. Developers can inspect assigned projects only; buttons, drag/drop, React Flow move/connect/delete/keyboard capabilities, property handlers and reducer mutation paths are gated. There is no saved graph to inspect yet, so a newly opened developer canvas is correctly empty. Client memory restrictions are UX, not protection against DevTools; future graph GET/write authorization must run on the server.
- Every draft is discarded on refresh/navigation. No graph data enters browser storage, backend graph routes or PostgreSQL. No package, new execution engine, SQL/API-key endpoint or database table is added.

## Proposed M4B graph-storage contract — not implemented

This proposal is a future bounded milestone, not authorization to implement it. Keep PostgreSQL/Npgsql and the current project/member model. A graph is one versioned design document for an existing UUID project, not executable code.

### Association and data

Add one explicit additive migration for a `project_graphs` table: `project_id uuid PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE`, `schema_version integer NOT NULL`, `revision bigint NOT NULL`, `document jsonb NOT NULL`, `updated_at timestamptz NOT NULL`. Require schema_version=1, revision>=1 and document object shape. No changes to existing business-table columns or historical helper tables. The bootstrap role owns DDL; grant the existing restricted API role only necessary graph CRUD. Review project-deletion cascade deliberately and test it; do not reset the volume.

Persist nodes (`id`, canonical existing `type`, finite `position.x/y`, `data.label`, approved configuration fields) and edges (`id`, source/target IDs, fixed `out`/`in` handles, approved existing edge type). Derive nodeDefinitionId, icons, descriptions and renderer implementations from the trusted type catalog rather than accepting implementations from storage. Keep metadata declarative and versioned.

Start with an explicit per-type field allowlist: trigger path/method, HTTP URL/method and nonsecret header names/values, response status/nonsecret headers, table name/validated column descriptors. Query/custom-logic nodes remain disabled placeholders; initially do **not** save their code/SQL source. Reject nonempty unsupported execution fields with a clear validation error rather than silently discarding them. Request bodies/parameters and new execution-related data need separate design review before persistence. This deliberately small initial storage contract should be confirmed during M4B planning.

Do not store cookies, CSRF/auth/invitation tokens, passwords, API keys, DB connections, Authorization/Cookie headers, credential-bearing URLs, real records, executable functions/React components, callbacks, runtime results or generated APIs. A narrow allowed-header list is preferable to attempting to recognize secrets in arbitrary text. Exclude React Flow transient selection/dragging/dimensions/internals, DOM measurements and UI error/loading state. Labels and allowed notes remain escaped plain text on reload; persistent data never becomes code or HTML. No automatic schema/application of table/query nodes.

### Routes and authorization

Propose GET and PUT `/api/auth/projects/{projectId}/graph`. A read of an authorized project without a saved graph returns a documented empty envelope with revision 0. Missing, foreign or unassigned projects return the same concealed 404. GET validates current DB account/organization and, for developers, current assignment. PUT is administrator-only in the current DB organization; derive organization from validated membership and constrain SQL joins/transaction statements by project and organization. Never accept client organization/role/owner as authority. Ordinary cookie validation, absolute revocation/expiry, request size limits, no-store and CSRF on PUT remain required. If using PUT, add only that verb to the existing explicit localhost CORS method list; do not widen origins or credentials.

Until those endpoints exist, M4A's scoped project read protects current project visibility and the UI gates local mutation only. It cannot secure a hypothetical save route. Test M4B GET/PUT with anonymous, developer write, stale membership, missing/invalid CSRF, unassigned, cross-organization and removed-project cases before claiming stored-graph authorization.

### Validation, conflicts and reload

Use strict DTOs/allowlists and parameterized Npgsql JSONB values. Reject unknown fields/types, duplicate IDs, bad handle directions, dangling endpoints, self/duplicate/cyclic edges, nonfinite positions and disallowed property shapes. Apply both per-field bounds from M4A and an aggregate **12 KiB UTF-8 serialized graph limit**, leaving room under the API's existing 16 KiB body limit; worst-case per-field/node maxima cannot all be used simultaneously. Do not raise global request limits silently. Validate JSON nesting (e.g. depth <=16), header/column counts and column property types explicitly. Validate the entire document before any write and return safe 400/413 without echoing content. Revalidate stored documents before rendering; unsupported schema versions get an explicit error rather than evaluation or speculative repair.

Return a monotonic revision with every graph. PUT carries expectedRevision and the full replacement document. Use a transaction and compare-and-swap (`UPDATE ... WHERE project_id=@project AND revision=@expected`, increment on success); initial create requires revision 0 and a uniqueness guard. Concurrent edits return 409, preserving the caller's local draft and offering explicit reload/review; do not blindly retry/merge writes. Keep schema version distinct from revision. A successful write returns its new revision/updatedAt. No collaborative engine or execution system is needed.

After an authorized project opens or refreshes, GET the graph, validate/normalize the approved shape into a fresh editor state, show loading/empty/error states, and enable mutation only for administrators. Developers get the same saved design in read-only mode if still assigned. Mark unsaved edits; use an explicit Save action initially rather than autosave. Project/identity changes must discard old access/results and never reuse another project's document. Network/save conflicts must not pretend success. No browser credential or graph cache is required.
